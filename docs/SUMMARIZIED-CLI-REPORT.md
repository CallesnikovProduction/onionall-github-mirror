## 0. Обращение к владельцу проекта

Привет.

Я хочу показать тебе, что именно было сделано с CLI Onionall Brawler, почему некоторые решения выглядят именно так и какие инженерные гарантии мы получили в результате.

Эта работа началась с довольно практической задачи: предоставить удобный способ взаимодействия с Onionall Brawler через терминал. Но постепенно CLI перестал быть простым набором команд.

Теперь это отдельный пользовательский интерфейс с собственными правилами работы с файлами, контролируемым сетевым транспортом, интерактивной графикой, офлайн-анализом HTML и набором автоматизированных проверок.

При этом я старался сохранить важную границу: **красивый интерфейс не должен вмешиваться в безопасность сетевого ядра, а новые возможности не должны преждевременно обходить ограничения архитектуры crawler.**

Именно поэтому некоторые потенциальные функции намеренно не реализованы.

Например, обнаруживать ссылки в HTML мы уже умеем. Но превращать каждую найденную ссылку в новое задание для распределённого crawler пока нельзя — для этого нужны дополнительные гарантии со стороны Frontier.

В этом отчёте я разделю то, что действительно реализовано и проверено, то, что существует в виде ограниченных диагностических возможностей, и то, что ещё предстоит завершить.

Моя задача — не просто сделать CLI впечатляющим. Я хочу, чтобы ты мог развивать этот продукт и через год, понимая, какие решения лежат в его основе и на какие проверки можно опираться.

## 1. Общий результат

### Что представляет собой CLI сегодня

Onionall Brawler CLI — самостоятельный терминальный интерфейс для выполнения ограниченных операций с HTML-ресурсами, анализа сохранённых страниц и диагностики окружения.

Реализованы четыре основные команды:

|Команда|Назначение|
|---|---|
|`fetch`|Однократное получение разрешённой HTML-страницы через TorProtocol|
|`inspect`|Локальный анализ сохранённого HTML|
|`status`|Диагностика доступности локальных компонентов|
|`discover`|Детерминированное извлечение, нормализация и классификация ссылок из локального HTML|

Дополнительно реализованы интерактивное меню, оформление терминала, установщик и автономный runtime-дистрибутив.

CLI не требует запуска Storm-топологии для обычного офлайн-анализа сохранённой страницы.

Это принципиальное решение.

Не каждая операция с HTML должна запускать распределённую инфраструктуру. Простые задачи должны оставаться простыми, а сложная система должна подключаться только там, где она действительно нужна.

## 2. Архитектура: как устроен CLI

Я разделил взаимодействие с пользователем, обработку HTML, файловые операции и сетевой транспорт.

Это позволяет проверять каждую область независимо и не смешивать ответственность.

Упрощённая схема выглядит следующим образом:

```
                  ONIONALL BRAWLER CLI
                           |
                +----------+----------+
                |                     |
          Interactive UI         Direct Commands
                |                     |
                +----------+----------+
                           |
                      Picocli
                           |
          +----------------+----------------+
          |                |                |
        fetch           inspect         discover
          |                |                |
     TorProtocol       Local HTML       Local HTML
          |                |                |
       SOCKS5             JSoup           JSoup
          |                |                |
   Approved onion       Metadata      Link extraction
          |                |                |
      HTML gates       File reads    TorPolicy validation
          |                                 |
      File output                    JSON / JSONL report
```

Команда `status` находится отдельно: она диагностирует окружение и не должна автоматически интерпретировать доступность TCP-порта как доказательство исправности всей Tor-сети.

### Технологическая основа

Для реализации использованы:

- **Java 25** — целевая JVM.
    
- **Picocli 4.7.7** — разбор команд и аргументов.
    
- **JSoup** — анализ HTML и определение кодировки.
    
- **TorProtocol** — существующий защищённый транспорт.
    
- **Java Console и ANSI** — терминальный ввод и отрисовка.
    
- **Java2D** — построение изображения маскота без графического окна.
    
- **Bash, Maven и Python unittest** — сборка, доставка и проверка.
    

Я сознательно не добавлял отдельный тяжёлый терминальный фреймворк вроде JLine или Jansi.

Для текущих требований оказалось достаточно возможностей существующего стека.

Это уменьшает число зависимостей, сокращает поверхность совместимости и делает дистрибутив проще.

## 3. Команда `fetch`: контролируемый сетевой запрос

`fetch` — первый важный мост между пользователем CLI и существующей сетевой инфраструктурой Onionall Brawler.

Её назначение — получить одну явно запрошенную HTML-страницу в рамках действующей политики.

### Последовательность выполнения

```
Пользователь задаёт URL
          |
          v
Проверка URL и scope
          |
          v
TorProtocol
          |
          v
SOCKS5 с передачей hostname
          |
          v
HTTP-ответ
          |
          v
Проверка MIME и размера
          |
          v
Атомарное сохранение файла
          |
          v
Результат пользователю
```

### Какие ограничения сохранены

При добавлении CLI я не изменял транспортную политику TorProtocol.

Продолжают действовать следующие ограничения:

1. Допускаются только источники, разрешённые текущей политикой Ahmia.
    
2. Onion-hostname передаётся через SOCKS5, а не подменяется локальным DNS-разрешением в рассматриваемом сценарии.
    
3. Прямое соединение в обход прокси не допускается.
    
4. Автоматические HTTP-перенаправления не выполняются.
    
5. Не добавляются скрытые автоматические повторы.
    
6. Действуют ограничения времени запроса.
    
7. Действуют проверки MIME и размера ответа.
    
8. CLI не превращает одиночный запрос в рекурсивный crawler.
    

Таким образом, `fetch` — диагностическая операция пользователя, а не полноценный robots-aware механизм распределённого обхода.

### Почему это важно

Я не хотел, чтобы появление удобной кнопки в терминале случайно дало пользователю возможность обойти ограничения, заложенные в crawler.

Команда должна оставаться настолько безопасной, насколько это позволяет существующая транспортная модель.

## 4. Что удалось проверить на реальном Tor-запросе

После локальных тестов установленный CLI выполнил запрос к разрешённой корневой странице Ahmia.

Зафиксированный результат:

```
{
  "http_status": 200,
  "bytes": 4735,
  "elapsed_seconds": 5.554051019,
  "title": "Ahmia — Search Tor Hidden Services",
  "saved": ".runtime/cli/ahmia-live.html",
  "passed": true
}
```

Запрос завершился с кодом `0`. Стандартный поток ошибок был пуст.

Для меня здесь важен не только статус HTTP 200.

Это проверка цепочки:

**установленная команда → транспорт → Tor → HTTP → HTML → локальный файл → структурированный результат.**

Во время первых испытаний выявились две ошибки упаковки зависимостей: отсутствовали `commons-cli` и `commons-lang3`.

Обе проблемы были исправлены в составе дистрибутива, после чего проверки повторили.

Я не стал выдавать первоначальные сбои за сетевые ошибки Tor. Их причина находилась в packaging, и именно там они были исправлены.

Такой подход важен для дальнейшей диагностики: если каждый сбой называть «проблемой Tor», мы перестанем видеть реальные дефекты приложения.

### Чего эта проверка не доказывает

Один успешный запрос не означает, что весь распределённый crawler прошёл M2 или M3.

Он также не доказывает отсутствие DNS-утечек во всей системе.

Эти утверждения требуют других, более широких проверок.

## 5. Безопасная работа с файлами

Сохранение HTML реализовано так, чтобы избежать ложного впечатления успешного завершения операции.

Используются временные файлы в том же каталоге, куда должен попасть конечный результат.

После завершения записи выполняется публикация готового файла.

### Два режима

**Без перезаписи:** публикация через создание жёсткой ссылки на подготовленный файл с атомарной семантикой create-if-absent.

**С разрешённой перезаписью:** атомарная замена конечного файла.

Это позволяет не демонстрировать пользователю недописанный результат как полноценную загрузку.

Есть и условие: файловая система должна поддерживать необходимые операции. Если это не так, сохранение должно завершаться ошибкой, а не маскировать её.

При прерывании запроса через SIGINT тесты проверяют отсутствие готового выходного файла, который ошибочно выглядел бы успешным результатом.

Сохранность данных для меня важнее красивого сообщения «Готово».

## 6. Команда `inspect`: локальный анализ HTML

`inspect` позволяет анализировать уже сохранённую страницу без подключения к Tor.

Команда использует JSoup и ограничивает размер входного файла четырьмя мебибайтами.

Она извлекает:

- заголовок страницы;
    
- описание;
    
- сведения о ссылках `href`;
    
- определённую кодировку документа;
    
- основные HTML-метаданные.
    

В терминальном выводе управляющие символы очищаются, чтобы содержимое внешнего HTML не могло произвольно управлять отображением.

### Архитектурная ценность

`inspect` показывает, что анализ документа и его получение — две разные задачи.

Мы можем сохранять страницы один раз, а затем многократно исследовать их содержимое, не создавая новых сетевых запросов.

Это полезно для воспроизводимых проверок, отладки парсера и будущих исследовательских сценариев.

## 7. Команда `discover`: следующий этап развития

`discover` — наиболее содержательное функциональное расширение CLI в этом наборе работ.

Её задача — не просто перечислить ссылки из HTML, а подготовить детерминированный отчёт о том, какие адреса были обнаружены и какие из них потенциально подходят для дальнейшей обработки.

Пример команды:

```
onionall discover ./saved.html \
  --base-url http://juhanurmihxlp77nkq76byazcldy2hlmovfu2epvl5ankdibsot4csyd.onion/ \
  --json
```

### Как устроена обработка

```
Сохранённый HTML
       |
       v
Извлечение href
       |
       v
Разрешение относительных URL
       |
       v
Нормализация URI
       |
       v
Структурная проверка onion-v3
       |
       v
Проверка TorPolicy и scope
       |
       v
Дедупликация
       |
       v
Проверка URL-only eligibility
       |
       v
JSON / JSONL
```

### Ограничения входных данных

Чтобы анализ оставался предсказуемым, введены явные границы:

|Параметр|Ограничение|
|---|---|
|HTML-файл|До 4 MiB|
|Длина URL|До 2 048 символов|
|Обрабатываемые anchors|Не более 1 000|
|Сетевые обращения|0|
|Рекурсивный обход|Отсутствует|
|Запись в Frontier|Отсутствует|

Если документ содержит больше ссылок, отчёт фиксирует ограничение через поля `processed` и `truncated`.

Частично обработанный результат не должен выглядеть как полный.

### Нормализация URL

Реализованы правила, которые позволяют сравнивать адреса без бессмысленных различий.

Например:

- схемы и hostname приводятся к нижнему регистру;
    
- стандартные порты удаляются;
    
- пустой путь превращается в `/`;
    
- фрагменты после `#` исключаются;
    
- относительные и protocol-relative ссылки разрешаются относительно базы;
    
- порядок query-параметров сохраняется;
    
- регистр пути и percent-encoded последовательности не изменяются произвольно.
    

Отдельно обработан случай query-only ссылок: они должны сохранять путь исходного документа, а не случайно заменять его при разрешении URI.

### Проверка onion-v3

Для потенциальных onion-адресов выполняется структурная проверка, включая версию и checksum.

При этом обнаруженный onion-hostname не становится автоматически разрешённым для обращения.

Проверка корректности адреса и разрешение доступа к нему — совершенно разные операции.

Я сохранил эту границу специально.

**Валидный onion-адрес ещё не означает, что crawler имеет право или техническую готовность его обходить.**

## 8. Дедупликация и математические инварианты

`discover` ведёт отдельный учёт обнаруженных ссылок, повторов, отклонений и области допустимых адресов.

Для обработанных ссылок действует:

```
processed = unique + duplicates + rejected
```

Для уникальных корректных целей:

```
unique = in_scope + out_of_scope
```

Это простые, но ценные инварианты.

Они позволяют автоматически обнаружить нарушения в классификации ссылок.

Например, если `processed` не равен сумме трёх категорий, результат неконсистентен независимо от того, насколько убедительно выглядит человеческий отчёт.

### Что означает `eligible_for_admission`

Поле сообщает, что уникальный URL прошёл проверки области действия и консервативного правила по расширению.

Но оно **не означает**, что:

- robots.txt уже проверен;
    
- выделен глобальный durable budget;
    
- URL принят Frontier;
    
- запрос можно безопасно выполнить;
    
- сервер действительно вернёт HTML.
    

Фактическое поле `admission` в офлайн-отчёте остаётся `false`.

И это правильная граница ответственности.

## 9. Почему `discover` пока не записывает URL во Frontier

Здесь я намеренно остановился.

Текущий механизм локального discovery не даёт всех гарантий для полноценного распределённого допуска URL.

В частности, ADR-0002 фиксирует проблемы с атомарным долговременным резервированием глобального бюджета и неоднозначным исходом операций при timeout.

Представим, что клиент отправил запрос на добавление URL во Frontier, но не получил ответ.

Возможны два состояния:

1. URL был добавлен, а подтверждение потерялось.
    
2. URL не был добавлен.
    

Если эти варианты невозможно надёжно различить, следующий автоматический шаг может нарушить ограничения по количеству заданий или семантику повторов.

Поэтому CLI пока занимается **анализом потенциальных кандидатов**, а не принимает решения за распределённый crawler.

Я считаю это не отсутствующей функцией, а сознательно сохранённым архитектурным барьером.

Мы не должны превращать исследовательский инструмент в неконтролируемый механизм постановки заданий.

## 10. Детерминированные отчёты JSON и JSONL

Для `discover` реализован структурированный вывод.

Он сохраняет:

- исходный URL;
    
- исходную HTML-ссылку;
    
- нормализованную цель или `null`;
    
- результат проверки URI;
    
- отдельный результат проверки onion-v3;
    
- принадлежность scope;
    
- eligibility;
    
- причину принятого решения;
    
- признак отсутствия фактического admission.
    

Порядок ссылок соответствует порядку в исходном HTML.

В результат не добавляются случайные идентификаторы или текущее время, которые делали бы одинаковые прогоны различными.

**Одинаковые входные данные в одном и том же расположении должны давать одинаковый результат.**

Экспорт выполняется только по явному запросу пользователя, атомарно и без перезаписи существующего файла.

### Защита информации

Ссылки с символом `@` консервативно редактируются, чтобы снизить риск записи userinfo credentials.

Однако в query-параметрах исходного URL всё ещё могут присутствовать чувствительные данные.

Поэтому такие отчёты следует хранить в игнорируемой `.runtime/`, а не добавлять в Git.

Структурированность результата не делает его автоматически безопасным для публикации.

## 11. Интерактивный терминал: от обычного меню к собственному интерфейсу

Теперь о самой заметной части работы.

Я хотел, чтобы Onionall Brawler имел узнаваемый интерфейс даже без графического приложения.

Терминал стал для проекта самостоятельной визуальной средой.

### Основные элементы

- Фирменный заголовок ONIONALL BRAWLER.
    
- Луковичный маскот с глазами и улыбкой.
    
- Фиолетовая цветовая палитра.
    
- Псевдообъёмное написание названия.
    
- Адаптация к ширине терминала.
    
- Интерактивное меню.
    
- Контролируемое отображение результатов.
    
- Корректное восстановление терминала после выхода.
    

Всё это работает без отдельного GUI-framework.

### Адаптивная геометрия

Интерфейс поддерживает разные размеры терминала.

На широких экранах используется более подробное оформление.

На узких — компактная композиция.

При недостаточной высоте сокращается заголовок, чтобы сохранить место для полезной информации.

Испытания включали терминалы шириной 50, 80 и 120 колонок.

Это важно, поскольку оформление, идеально выглядящее в одном окне, может полностью разрушаться при другом размере.

Поэтому геометрию проверяли не только визуально, но и через терминальные тесты.

## 12. Маскот Onionall

Отдельная часть работы посвящена фирменному персонажу.

Сначала были исследованы несколько силуэтов: каплевидный, округлый и многослойный луковичный.

Затем появилась псевдообъёмная ASCII-версия.

После этого маскот получил собственную оригинальную векторную геометрию.

В итоговом варианте используются:

- вытянутые побеги;
    
- округлые слои луковицы;
    
- светлая область лица;
    
- контрастные глаза;
    
- изогнутая улыбка;
    
- цветовые поверхности и тени.
    

Изображение строится в памяти с использованием Java2D.

Рендеринг работает в headless-режиме: **для него не требуется открывать графическое окно или устанавливать соединение с X11**.

Для вывода используется комбинация терминальных полублоков `▀` и `▄`, позволяющая отображать две цветовые половины в одной символьной ячейке.

При этом предусмотрены упрощённые варианты для монохромных или ограниченных терминалов.

Переменная `ONIONALL_ASCII=1` включает ASCII-представление.

### Почему это решение интересно технически

Мы не копируем картинку в терминал.

Мы строим собственную геометрию, преобразуем её в терминальные ячейки и учитываем ограничения текстового устройства вывода.

Это даёт Onionall собственную визуальную идентичность без зависимости от внешних изображений, шрифтов или специального графического протокола.

В отчётах отдельно подтверждается, что пользовательский референс не был скопирован в репозиторий как изображение.

## 13. Фиксированный заголовок и управление экраном

Интерактивная оболочка поддерживает неподвижный фирменный заголовок при навигации.

Для этого используются ANSI-механизмы управления курсором, очистки отдельных строк и границ прокрутки.

Обычные обновления перерисовывают только изменённые строки содержимого.

Это предотвращает постоянное мигание терминала и ненужную полную перерисовку экрана.

### Важное изменение в истории реализации

В ранней версии интерактивный интерфейс работал непосредственно в основном экране терминала, без alternate screen.

Позднее был реализован **alternate screen buffer с последовательностью 1049**.

Последняя задокументированная реализация использует отдельный экран для поддерживаемых ANSI TTY-сеансов.

После выхода восстанавливаются прежний экран, положение курсора и доступная история терминала.

Это означает, что интерактивная оболочка не должна оставлять после себя повреждённый интерфейс терминала.

В тестах проверены:

- обычный выход;
    
- завершение по EOF;
    
- SIGINT;
    
- обработанные ошибки ввода;
    
- восстановление основного экрана.
    

Для `NO_COLOR`, неподдерживаемых терминалов и неинтерактивного режима сохраняется обычный линейный вывод.

### Отдельно о прогрессе

Во время `fetch` отображается прошедшее время операции.

Я не стал показывать выдуманные проценты загрузки.

TorProtocol не предоставляет CLI прямого потока прогресса по загруженным байтам, поэтому индикатор честно отражает только продолжительность ожидания.

Лучше показать ограниченную, но правдивую информацию, чем красивую ложную телеметрию.

---

## 14. Команда `status`: диагностика без ложных гарантий

Диагностика должна чётко различать уровни доступности.

Если TCP-порт отвечает, это ещё не доказывает, что:

- Tor построил рабочую цепочку;
    
- onion-сервис доступен;
    
- SOCKS-запрос будет успешным;
    
- crawler сможет получить корректный HTML.
    

Поэтому `status` явно отделяет локальную TCP-доступность от непроверенных состояний Tor и onion.

Для неподтверждённых проверок используется обозначение `NOT_TESTED`.

Это особенно важно для проекта с несколькими уровнями сетевой инфраструктуры.

Нельзя превращать одну успешную проверку порта в зелёный статус всей системы.

## 15. Сборка, установка и распространение

CLI упакован в отдельный дистрибутив.

В базовом отчёте зафиксирован размер около **56 MiB**.

В пакет входят необходимые runtime-зависимости, включая требуемые компоненты Storm API, StormCrawler, HTTP и HTML-парсинга.

При этом из дистрибутива исключены ненужные для CLI компоненты: Flux, Tika, Frontier/gRPC и тестовые библиотеки.

### Принцип установки

Установленный CLI запускается с Java runtime и не должен требовать Maven.

Для обычной Linux-установки зафиксированы пути:

```
~/.local/bin/onionall
          |
          v
~/.local/share/onionall/cli/bin/onionall
```

Установщик проверялся, в том числе, с XDG-путями, содержащими пробелы.

Отдельно проверялось сохранение посторонних файлов и символических ссылок при установке, обновлении и удалении.

### Требования окружения

Основная целевая версия — Java 25.

Испытание запуска через Java 17 подтвердило отказ с кодом завершения `69`.

Это помогает избежать непредсказуемого поведения при использовании неподходящего runtime.

Для растеризации маскота необходим JDK-модуль `java.desktop`. Стандартный JDK 25 его содержит; при сборке собственного минимального `jlink`-runtime модуль потребуется включить явно.

### Граница подтверждённой поддержки

В этих отчётах подтверждена Linux-установка.

Эквивалентная проверка Windows packaging здесь не заявлена.

Я не хочу записывать кроссплатформенную доставку как завершённую до появления соответствующих доказательств.

## 17. Неудачные испытания и исправления

Я считаю важным сохранять не только зелёные результаты, но и историю обнаруженных проблем.

Во время разработки были зафиксированы:

**Ошибки packaging.** Отсутствующие `commons-cli` и `commons-lang3` в установленном CLI. Исправлены через корректировку списка runtime-зависимостей.

**Проблема геометрии терминала.** Ранний вариант маскота выходил за границы при ширине 70 колонок. Размер композиции был согласован с доступной шириной и словесным логотипом.

**Графическое окружение.** При разработке Java2D-маскота возникала нежелательная зависимость от DISPLAY. Рендеринг переведён в явный headless-режим.

**Граница Kotlin/Java исключений.** Новый discovery test выявил несовпадение деклараций checked exceptions. Использован Java-адаптер, сохраняющий поведение IOException без изменения TorPolicy.

**Особенность тестовой конфигурации Picocli.** Новая тестовая настройка не учитывала значения по умолчанию. Для теста задана явная конфигурация политики.

**Проблема минимального PATH.** Первый reduced-PATH запуск не содержал `readlink` и завершился с кодом `127`. После добавления необходимой утилиты проверка окружения прошла.

Каждое такое исправление позволяет сделать инструмент менее зависимым от случайных особенностей машины разработчика.

Сбой — это не проблема, которую нужно спрятать из отчёта. Это возможность уточнить контракт системы и закрепить его тестом.

## 19. Как воспроизвести основные проверки

При выбранном JDK 25:

```
ONIONALL_OFFLINE=1 ./scripts/build-cli.sh

python3 -B -m unittest discover \
  -s test/cli \
  -p 'test*.py'

./scripts/install-cli.sh --no-build

onionall --help
```

Для запуска интерактивного режима:

```
onionall
```

Для офлайн-анализа сохранённого HTML:

```
onionall inspect ./saved.html
```

Для обнаружения ссылок:

```
onionall discover ./saved.html \
  --base-url http://juhanurmihxlp77nkq76byazcldy2hlmovfu2epvl5ankdibsot4csyd.onion/ \
  --json
```

Запуск `discover` не должен требовать Tor, Docker или Maven в установленном окружении.

Точный список поддерживаемых опций и кодов завершения следует сверять с актуальной справкой `onionall --help` и командными разделами README.

## 20. Что пока не завершено

В этом отчёте я намеренно отделяю успешную разработку CLI от незавершённых задач всей платформы.

|Область|Статус относительно этого отчёта|
|---|---|
|Локальный HTML-анализ|Реализован и проверен|
|Офлайн-обнаружение ссылок|Реализовано и проверено|
|Упакованный Linux CLI|Проверен|
|Контролируемые SOCKS5-запросы|Проверены|
|Один реальный разрешённый Tor-fetch|Подтверждён|
|Полный M2 Recovery acceptance|Не закрыт этими проверками|
|Реальный распределённый M3 crawl|Не закрыт|
|Durable global admission|Не реализован в CLI|
|Полноценная проверка отсутствия системных DNS-утечек|Не доказана|
|Windows packaging|Не подтверждён представленными отчётами|

Особенно важен ADR-0002.

До появления надёжного механизма глобального атомарного допуска не следует представлять офлайн-обнаружение ссылок как готовый production crawling pipeline.

CLI способен находить и классифицировать кандидатов.

Но право превращать их в распределённые задания должно принадлежать системе, которая умеет корректно управлять бюджетами, повторами, подтверждениями и состоянием Frontier.

## 21. Что я считаю главным достижением

Мы получили не просто терминальную оболочку вокруг HTTP-запроса.

У Onionall Brawler теперь есть самостоятельный CLI-компонент с несколькими полезными свойствами.

**Во-первых, он отделён от тяжёлой инфраструктуры.** Для просмотра и анализа сохранённого HTML не требуется поднимать Storm, URLFrontier и Tor.

**Во-вторых, он придерживается существующих защитных ограничений.** Удобство взаимодействия не стало причиной ослабления TorProtocol или политики доступа.

**В-третьих, его результаты проверяемы.** Есть JVM-тесты, PTY-тесты, SOCKS fixtures, проверка упаковки и конкретные evidence-файлы.

**В-четвёртых, у продукта появился характер.** Собственный маскот, фирменная терминальная графика, адаптивный интерфейс и корректное управление экраном делают Onionall узнаваемым даже в обычной консоли.

**В-пятых, реализация сохраняет пространство для роста.** `discover` уже формирует структурированные сведения о ссылках, но не подменяет собой будущий механизм безопасного admission.

Это хороший инженерный фундамент.

Не потому, что здесь много строк кода или эффектная графика.

А потому, что функциональность, ограничения и способы проверки начинают образовывать целостную систему.

## 22. Заключительное обращение

За время этой работы CLI Onionall Brawler прошёл путь от первоначального интерфейса с тремя командами до отдельного инструмента, объединяющего сетевую диагностику, локальный анализ HTML, офлайн-discovery и интерактивное терминальное представление.

Часть решений оказалась сложнее ожидаемого. Пришлось исправлять упаковку зависимостей, отрабатывать поведение реального терминала, учитывать геометрию символов, обрабатывать сигналы завершения и жёстко разграничивать локальный анализ с сетевым обходом.

Но именно эти детали отличают демонстрационный прототип от инструмента, который можно постепенно доводить до промышленного качества.

Я также намеренно не стал закрывать незавершённые M2/M3 вопросы красивыми формулировками.

Они остаются самостоятельными инженерными задачами.

**Важнее иметь систему, которая достоверно сообщает о своих ограничениях, чем систему, которая всегда показывает зелёный статус.**

У Onionall Brawler уже появился узнаваемый интерфейс и проверяемый набор возможностей. Следующая задача — довести распределённую часть платформы до того же уровня строгости.

И тогда CLI станет не просто удобной оболочкой, а полноценной точкой управления более крупной системой.

**Я берегу этот проект прежде всего через его инварианты: сохранность данных, воспроизводимость результатов, честность проверок и возможность безопасно продолжать разработку.**

Это та инженерная основа, на которой Onionall Brawler стоит развивать дальше.
