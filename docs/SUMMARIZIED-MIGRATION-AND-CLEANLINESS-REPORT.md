### Привет!

В этот раз я хочу рассказать не о новой команде CLI или очередном успешно загруженном документе.

Мы занимались фундаментом самого Onionall Brawler: обновляли технологическую платформу, проверяли накопленные инженерные вопросы и приводили репозиторий в состояние, в котором дальнейшая разработка будет безопаснее и предсказуемее.

Это работа, которую не всегда видно пользователю.

Но именно она определяет, можно ли будет через несколько месяцев спокойно добавлять новые возможности, не опасаясь, что очередное обновление сломает половину системы.

**Главный результат: Onionall Brawler перешёл на Java 25 и Apache Storm 3.1, сохранил подтверждённую работоспособность ключевых локальных сценариев и получил более строгую картину своего технического долга.**

Причём обновление выполнялось без разрушения предыдущего стабильного состояния.

### 1. Переход на современную JVM-платформу

Я обновил технологическую основу проекта:

|Компонент|Ранее|После миграции|
|---|---|---|
|Java|17|**Temurin 25.0.5 LTS**|
|Apache Storm / Flux|2.8.9|**3.1.0**|
|Storm Docker image|JRE 17|**JRE 25**|
|StormCrawler|3.7.0|3.7.0|
|Kotlin|2.3.21|2.3.21|
|URLFrontier|2.4|2.4|

Здесь важно, что я не стал обновлять все зависимости одновременно.

StormCrawler 3.7.0 изначально ориентирован на Storm 2.8.9 и Java 17. Поэтому совместимость с новой платформой мы подтверждали не предположениями, а реальными проверками исполняемой топологии.

JVM-классы приложения были собраны с bytecode version 69, соответствующей Java 25.

Само обновление Storm не потребовало изменения основных компонентов crawler.

Для отката сохранился предыдущий checkpoint `97b9da4`. Главная ветка не переписывалась.

**Мы обновили фундамент, не уничтожая возможность вернуться к проверенной старой конфигурации.**

### 3. Java 25 и защита DNS

Во время миграции пришлось отдельно пересмотреть диагностический механизм контроля DNS.

Старый тест использовал приватные механизмы Java 17, которые больше не подходили для новой JVM.

Вместо обращения к внутренним полям JDK я перевёл тестовый механизм на публичный интерфейс `InetAddressResolverProvider`.

<text color="secondary">Результат проверки</text>

- 35 тестов пройдены.
    
- Ошибок — 0.
    
- Попыток разрешить onion-hostname через контролируемый JVM resolver — 0.
    
- Проверены положительные контрольные сценарии.
    

Важно: специальный resolver подключается только в тестовой JVM и не устанавливается глобально в приложение.

Эта проверка подтверждает поведение конкретного сетевого сценария, **но не доказывает отсутствие всех возможных DNS-утечек на уровне операционной системы**.

### Что действительно исправлено

В `TorProtocol` была усилена обработка `robots.txt`.

Повреждённые UTF-8 и UTF-16 данные теперь отклоняются строгим декодером вместо молчаливой замены некорректных символов.

Ошибки парсера сохраняют исходную причину и классифицируются как `ROBOTS_UNAVAILABLE`, а не превращаются в разрешение обходить всё.

Это важно: повреждённый robots-файл не должен случайно ослаблять ограничения crawler.

### Отдельная победа — блокировки robots cache

2 ноября была устранена проблема глобальной синхронизации кеша robots.

Раньше медленная загрузка правил одного origin могла удерживать общий монитор и блокировать обращения к совершенно другому origin.

Теперь для загрузки используются отдельные блокировки по origin.

Проверки подтвердили:

- отсутствие блокировки независимых origin;
    
- объединение одновременных запросов к одному origin;
    
- корректное истечение TTL;
    
- отсутствие кеширования неуспешной загрузки;
    
- безопасное завершение при отмене;
    
- сохранение политики вытеснения кеша.
    

Результат — **41 тест TorProtocol PASS** в соответствующем офлайн-прогоне.

Для crawler это серьёзное улучшение: один медленный сайт больше не должен удерживать весь механизм получения robots-правил через прежнюю глобальную блокировку.

При этом настоящая Tor-интеграция и поведение под распределённой нагрузкой требуют отдельных испытаний.

### 5. Чистота репозитория: навели порядок, не трогая ценные данные

Отдельно я проверил рабочее дерево Onionall Brawler.

Задача была не в том, чтобы максимально освободить диск, а в том, чтобы отличить действительно ненужные файлы от важных результатов разработки.

В `.runtime` находились тысячи файлов, включая тестовые журналы, Maven-кеш, собранные инструменты и артефакты испытаний.

Я не стал удалять всё это одной командой.

После классификации были удалены только **62 файла**, для которых имелось достаточное обоснование:

- 24 временных Python bytecode-файла.
    
- 38 неиспользуемых файлов Maven-кеша постороннего проекта.
    

Последние занимали примерно 135,8 МБ.

### Важная проверка изоляции проектов

В Maven-кеше Onionall обнаружились артефакты MakeTalents.

Я проверил, участвуют ли они в реальной сборке Onionall Brawler.

Результат: активные зависимости, исполняемый JAR и проверенные конфигурации не содержали зависимостей от MakeTalents.

После удаления постороннего кеша проект успешно собрался повторно.

**Это был мусор в локальном кешe, а не доказанное смешение исходников двух проектов.**

Сам MakeTalents не изменялся.

### Что осталось нетронутым

Я сохранил:

- исходники, тесты и документацию;
    
- Docker volumes;
    
- данные RocksDB;
    
- конфигурацию Tor;
    
- onion-ключи;
    
- `.secrets`;
    
- evidence M1/M2/M3;
    
- необходимый Maven-кеш и проверенный JDK 25.
    

Не выполнялись массовый `git clean`, удаление Docker volumes или изменение системных сетевых настроек.

Для меня чистота репозитория — это не минимальное количество файлов. Это способность понимать происхождение и назначение каждого важного артефакта.

### 7. Что осталось открытым

Я не хочу создавать впечатление, что после обновления Java и очистки TODO Onionall Brawler автоматически готов к промышленной эксплуатации.

Остаются серьёзные задачи:

- M2 — повторяемое восстановление реального Tor-транспорта.
    
- M3 — полноценный onion A → B → C вместо локального HTTP-сценария.
    
- ADR-0002 — атомарный глобальный admission в URLFrontier.
    
- Проверка отдельных сетевых механизмов: SOCKS-ответов, TLS/HTTP2, follow-up запросов и lifecycle Storm.
    
- Точная оценка конфликтующих зависимостей URLFrontier API, protobuf и logging.
    
- Безопасная доставка и проверка обновлений Tor.
    
- Испытания в настоящем распределённом Storm и на Windows 25.
    

Обнаруженные TODO со статусом BLOCKED — это не обязательно найденные уязвимости. Чаще это вопросы, для которых пока недостаточно доказательств.

Именно поэтому они сохраняются в техническом реестре долга с конкретными критериями закрытия.

Эта работа не добавила десятки новых пользовательских функций.

Проект растёт, и вместе с ним должна расти инженерная дисциплина.

Я хочу, чтобы следующие возможности Onionall Brawler строились не поверх неизвестных проблем, а поверх платформы, которую мы действительно понимаем.

**Модернизация — это не просто переход на более свежие версии. Это сохранение управляемости проекта в момент, когда он становится сложнее.**
